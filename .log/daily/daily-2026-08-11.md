## Three verification lessons, all the same species 👁️

The most valuable thing this day produced, and none of it is in the diff.

1. **`h-full` looked like the clean way to size the report and does not work here.** `<main>` is
   `flex-1` under a `min-h-full` body, so its height is never definite; the percentage silently falls
   back to auto and the report collapses to a ~150px default iframe box. The page appeared to "fit"
   only because the content had gone short. Reverted to `lg:h-[calc(100dvh-9.125rem)]`. #bug
2. **9.125rem is measured, not estimated.** The first guess was 8.9rem and it overflowed by exactly
   4px at every viewport. The real boxes were read over CDP — nav 57px (`h-14` + 1px border), footer
   89px (1px + `py-8` + a 24px line) = 146px. The comment says so, and says the number moves if either
   changes.
3. **Screenshots cannot answer "does this scroll?"** Headless clamps the capture to the window, so
   `/services`, `/blog` and `/work` all returned exactly 1440×900 too. The working method is reading
   `documentElement.scrollHeight` against `innerHeight` over the DevTools Protocol — **with a control
   page that must scroll.** `/services` was that control, and without it the first "fits" reading
   would have been believed.

Verified across 1920/1600/1440/1366/1280 in both locales: no scroll anywhere; the report grew from
476px to 558px at 1440×900 once the clutter was gone. **What is verified is the layout box, not the
dashboard** — the embed only rendered its own loading logo in headless.

The viewport lock is `lg`-and-up only. A Power BI dashboard squeezed into a phone viewport is
unreadable, so below `lg` the page keeps ordinary flow and the report keeps `aspect-video`.
