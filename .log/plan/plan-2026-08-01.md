## Goal D — Syndication: autopost blog posts & showcases  ·  **NEW, big, implementation later**

**Ask (2026-08-01):** a mechanism that automatically posts new **blog posts** and **showcases** to
**LinkedIn**, **X (Twitter)** and **Dev.to**.

Captured now, built later. Nothing below is decided — this section exists so the decisions are made
once, deliberately, instead of being invented mid-implementation.

### Why this is not a small task

The publishing part is easy. The hard parts are **state**, **cost** and **irreversibility**:

- **It has no database.** The repo is deliberately DB-free (`CLAUDE.md`), so "which posts have
  already been syndicated" needs a home. Candidates: a committed `syndication.json` manifest (git is
  the state store — auditable, reviewable in a PR, no infra), a git tag per post, or querying each
  platform's API. The manifest is the obvious first choice; the others are listed so the choice is
  visible.
- **Posting is irreversible and public.** This fires under the user's professional identity on a site
  whose entire job is credibility. A dry-run mode and an explicit approval gate are not polish here —
  they are the feature. A bad automated LinkedIn post costs more than the automation saves.
- **Two of the three platforms may cost money or be gated.** See the per-platform table.

### Per-platform reality check — **verify all of this before committing to the design**

| Platform | Mechanism | Known friction (as of last check — **re-verify, this moves**) |
|---|---|---|
| **Dev.to** | Forem API, simple API key, full-article cross-post | Easiest by a distance. Free. Accepts markdown + `canonical_url`. **Start here.** |
| **LinkedIn** | Share/Posts API, OAuth 2 | Posting to a *personal profile* needs an approved app with `w_member_social`; access review is a real gate. Tokens expire — refresh handling required. A Company Page is a different (often easier) path than a personal profile. **Decide which identity posts.** |
| **X (Twitter)** | API v2 write | **Write access is a paid tier.** Last known ~$100/mo for Basic. This is the same shape of decision as `ADR-0003`, where Preset.io was dropped at $500/mo for a demo — **price it before building it**, and be willing to drop X the same way. |

### Open decisions — none of these should be answered by whoever writes the code

1. **Trigger.** On deploy (Vercel deploy hook), on merge to `main` (GitHub Actions), on a schedule, or
   manual-with-a-button? GitHub Actions is the natural fit if the state manifest is committed, because
   it can write the manifest back; Vercel functions cannot commit to the repo.
2. **Approval gate.** Fully automatic, or open a PR / post a draft for the user to approve? Given
   irreversibility, lean toward a gate at least until it has proven itself.
3. **Showcases are not articles.** Blog posts have an MDX body; `work.ts` showcases have a title, a
   summary and 2 paragraphs. Dev.to expects an article — a showcase may not have enough substance to
   cross-post as one. Likely answer: showcases go to LinkedIn/X as a link + blurb, and **not** to
   Dev.to. Decide explicitly.
4. **Locale.** EN only, or both? Posting Russian copy to Dev.to is probably wrong; LinkedIn may
   differ. Note the blog bodies are still English-only anyway (Goal B4).
5. **Canonical URLs — non-negotiable once chosen.** Any full-text cross-post (Dev.to) **must** set
   `canonical_url` back to `vosk.dev`, or the syndicated copy competes with the original in search.
   This is the single most expensive mistake available in this feature.
6. **Copy per platform.** X has a length limit and different tone; LinkedIn rewards longer framing.
   One shared blurb, or per-platform text authored in frontmatter?
7. **Secrets.** Four-ish credential sets. Where do they live — GitHub Actions secrets or Vercel env?
   Follows from decision 1. They must not go anywhere near `lib/env.ts`, which is client-reachable.
8. **Failure policy.** One platform failing must not block the others, and must not mark the post as
   syndicated. Partial success needs to be representable in the manifest.

### Likely shape (sketch only — do not treat as a design)

A `lib/syndication/` seam with one adapter per platform behind a common interface, driven by a
committed manifest, invoked by whatever decision 1 lands on. Same instinct that made the Preset → VPS
swap cost ~60 lines: keep every platform behind a boundary so dropping X (or adding Mastodon/Bluesky)
touches one file.

**Write an ADR when this starts** — it is a multi-vendor, recurring-cost, public-facing decision, which
is exactly the bar `ADR-0001`–`ADR-0003` were written at. Price X and check LinkedIn's app-review
gate *first*; both could change the scope from three platforms to one.
