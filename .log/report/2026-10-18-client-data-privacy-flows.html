Working with clients' data, privacy first

How to run an agentic dev process (Claude Code, Codex, local models) on clients' databases without the data ending up in places the client never agreed to.

Findings of 2026-10-18 · VOSK.DEV internal · not legal advice: have a lawyer write the DPA.

The starting plan (the owner's): the client provides limited, anonymized tables, schemas or views → I query, transform and merge them → I ship the solution to the client's cloud as files or publish it to a workspace or account the client manages (MS Fabric, Google BigQuery).

Verdict: the right default. It has three gaps, and closing them is most of the work.

1. The three gaps

  1. "Anonymized" is usually pseudonymized. Masked or hashed data that can be linked back to a person is still personal data under GDPR. Merging sources makes it more identifiable: every join adds context.
  2. The plan covers what the client hands you, not the copies your tools make. With agents, that's the main exposure:
    • every query result the agent reads goes to the model provider;
    • it is written to a plaintext transcript in ~/.claude/projects/ (kept 30 days by default);
    • it sits in dbt target/, DuckDB files, CSV extracts and the PBIP .pbi/cache.abf;
    • OneDrive or another sync tool copies all of it off the machine.
  3. The paperwork. If personal data reaches Anthropic or OpenAI, they become your subprocessors, and the client has to authorize that in writing.

2. The core rule

The agent sees code, schema and aggregates. It never sees rows.

The sqldev-mcp case already proves it works: a 2,200-line query was optimized from catalog data, planner statistics and plans alone, with no data read.

The agent may seeThe agent never sees
DDL, column types, row counts, sizes, planner statisticsRow-level values of real client data
Query plans, run timesselect * output, samples, extracts
Aggregates with a minimum group sizeSmall groups that single out a person
Synthetic or fully masked dataThe contents of cache.abf, target/, .duckdb

3. Four access levels, one chosen per client and written into the contract

LevelWhat you getGood for
0 · MetadataSchema, statistics, plans. A read-only login with no select on data tablesOptimization, modeling, reviewing SQL and DAX
1 · SyntheticFake data generated locally from that schema and its statisticsdbt and SQL dev, PBIP layouts, tests
2 · Client-masked viewsthe owner's planA dedicated dataset or schema the client masks at the sourceJoins and logic that need realistic values
3 · Inside their tenantA guest account or their VM; data never leavesFinal checks against real data, then shipping

Level 2: how the client masks at the source

  • BigQuery: authorized views plus policy tags. These drive column-level access and dynamic masking, and access is managed per tag tier.
  • Fabric Warehouse: dynamic data masking, row- and column-level security, and a Viewer role (T-SQL reads only, not raw OneLake files).
  • Join keys: keyed hashing (HMAC), with the key kept by the client. The same customer gets the same token in every source, so merges still work, but the tokens can't be reversed.
Caveat: masking and row-level security have known bypasses. Treat them as defense in depth, not as a guarantee.

Level 3

This is where real data meets your code. You work in their Fabric workspace or BigQuery project, under their identity provider, which they can switch off on the last day.

Per-project .claude/settings.json

  • Deny reads of *.csv, *.parquet, *.duckdb, **/.pbi/cache.abf, target/**, .env*.
  • Deny direct psql, bq query, sqlcmd, so every query goes through the MCP.
  • Set cleanupPeriodDays low, and set CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1.

sqldev-mcp as the enforcement point

It is already read-only, returns digests instead of dumps, and keeps one connection per database. Add a "no rows" mode per connection: catalog and plan tools only, a cap on result size, and refusal of small groups. Then the access level is enforced by the tool, not by discipline.

Local models (Ollama and similar)

They are for the jobs that have to touch rows: detecting personal-data columns, masking, profiling. The frontier models write the code; the local model handles the data.

The PC

  • One folder, one repo and one credentials set per client. A dev container or a separate Windows user is better.
  • BitLocker on. Client folders outside OneDrive.
  • A documented wipe at the end of the engagement.

5. Mixing cloud and local data

  • Never copy client production data to the PC to develop against it.
  • One set of dbt models, two targets:
    • dev: DuckDB on the PC, fed with synthetic or level-2 seeds;
    • prod: their BigQuery or Fabric (dbt-bigquery / dbt-fabric).
  • dbt contracts and tests, so a model that passes on synthetic data is checked against real data in their tenant.
  • Mix in one direction only. Your reference data (calendars, mappings, FX rates) goes up into their tenant; their data never comes down to be merged with yours.

6. Shipping

  • Code goes into a repo the client owns (their GitHub or Azure DevOps). Deploy through Fabric Git integration or deployment pipelines, under their service principal.
  • PBIP: keep .pbi/cache.abf ignored. PBIP's default .gitignore does this, but a file committed before the rule existed stays tracked (git rm --cached). Watch for "Enter data" tables, which keep their rows inside the model files. Never ship a PBIX: it contains the data.
  • A pre-ship scan in CI: gitleaks, plus checks for data-file extensions, emails and the client's ID patterns.

7. Paperwork, once per client

  • A data processing agreement (DPA): you as processor, your AI vendors listed as subprocessors with the hosting region, the access level, a deletion date with written confirmation.
  • A client-facing one-page data-handling policy. Also a selling point for the site: "your data never leaves your tenant; my AI tools see your schema, not your customers."

8. The default flow

Level 0–1Schema, statistics, synthetic data. Local agent.
Level 2Only when real values matter: client-masked views, HMAC keys, read-only via sqldev-mcp.
Level 3Validate and ship in their tenant, their repo, their service principal.
CloseDocumented wipe, deletion confirmation, credentials revoked.
