Data agents make stuff up. Not always. Just often enough that you can't put the
answer in front of management without checking it yourself, which kinda kills
the point.

Most of it comes from one habit: the agent writes its own SQL. It reads the
schema, guesses what the metric means and runs whatever it came up with. Ask for
last quarter's cost per click across all channels and you'll most likely get
`sum(spend) / sum(clicks)`. In my demo data only 2 channels out of 5 even have
clicks, so that number is inflated. It still looks like a CPC. The query ran,
the agent explains it with confidence, nobody asks.

A customer that doesn't exist gets caught quick. A made-up *definition*
doesn't.

## Take the SQL away

So my agents don't write SQL. At all.

Every metric is a function in the database. This is one of them, from the
[Tidewell data chat](/work/ceo-digest), a demo SaaS company with marketing, cash
and customer data in Postgres. Trimmed to the part that matters:

```sql
-- One row per channel and a 'total' row. cpc_eur and ctr_pct
-- cover the channels that have clicks (paid search and paid
-- social): on the total row cpc_eur is their spend ÷ their
-- clicks, not all spend. cac_eur = spend ÷ new customers.
create function fn_marketing_by_channel(p_from date, p_to date)
returns table (
     channel_code       text
    ,channel_name       text
    ,spend_eur          numeric(14,2)
    ,clicks             integer
    ,cpc_eur            numeric(14,2)
    ,new_customers      integer
    ,cac_eur            numeric(14,2)
    -- ...nine more columns
)
language sql stable security invoker
set search_path = ceo_digest_demo
as $$
    ...
$$;
```

The CPC rule lives there, written once, by me. So does the week rule (a week
belongs to the month its Thursday falls in, the ISO way) and the clamp that
stops any period from running past the last date in the data. Exactly the stuff
an agent would guess differently every other time.

The agent gets the function as a tool: a name, two typed dates and one line of
description.

> Marketing for a period, one row per channel plus a total: spend, impressions,
> clicks, CTR, CPC, MQLs, cost per MQL, trials started and converted,
> trial-to-paid rate, new customers, CAC, new MRR.

That list of tools is everything it gets. It never sees the schema, and there's
no tool to send raw SQL through. The database login behind it is read-only,
stuck in its own schema, with a statement timeout. Pick a tool, fill in the
dates, write a sentence around the rows. Done.

## Basically an MCP over your DB

Named functions, typed arguments, a description each. That's what an MCP server
exposes as tools. Mine happen to sit inside the site's chat route, but put the
same functions behind MCP and any agent can use them.

They already have two callers. The site's chat runs them to answer in the
browser. When a visitor asks for the data by email, an n8n workflow runs the
same functions as its own database role and builds the email from the rows. One
definition of CAC, two front doors.

(Back in October I wrote about
[a read-only MCP server that let an agent see the database](/blog/give-the-agent-eyes)
behind a Power BI model. That one is raw access, for me, while I build.
Functions are for the people asking questions about the numbers.)

## Does it work?

I built a few "chat with data" demos this way: a lender's sales report, a SaaS
marketing dashboard, a [management P&L](/work/pnl-suite) and a mining fleet
report. Each has an answer key, questions whose answers were worked out from the
data before the chat existed, run through the real chat loop like a visitor
would.

211 out of 222 right. The other 11 were format mismatches ("0.03 pp below plan"
vs a key that said "−0.03 pp"), or the metric didn't exist for that cut and the
chat said so and offered to adjust the ask. My favourite: asked for ad frequency
over one week, it answered that the measure needs at least 14 days and offered a
longer window. The rule lives in the function, so the agent can't fudge it.

No made-up numbers.

## The perks

Speed. Nothing to reason out, no query to write, run, fix and run again.
Each question gets 3 model calls and 4 tool calls max, and a small, cheap model
handles it fine. The whole 222-question test run cost about 8 cents. That's
around 2,800 questions per dollar.

Predictable. Same question, same function, same number. Tomorrow too, and
for the next person who asks.

You own the code. The logic sits in your database and your git repo, next to
the rest of your SQL. Not in a prompt, not in a vendor's black box. Change a
definition once and every agent, report and workflow that calls the function
gets the change.

You see the internals. Every answer traces back to the function it called
and the arguments it passed. On my site each tool call even shows up in the chat
as a card with its figures. Don't trust a number? Open the function and read it.

## The catch

Every question needs a function behind it. Ask Tidewell something none of its
functions cover and it'll tell you it can't. That's the point, but people used
to ChatGPT will notice the walls.

Writing the catalogue is the real work. Every metric needs its formula spelled
out and a test question or you'll never know if the agent picks the right one.
Descriptions need the same care as code: the tool that emails a report only
fires when the visitor asked, typed the address and confirmed it, and the
description says "ONLY when" in capitals, with a unit test checking the wording
is still there. And function signatures become a contract: rename a column and
the n8n workflow breaks on its next run.

Worth it. If you're gonna put the numbers in front of management for real
decisions, you gotta be sure what comes out. Define the logic once, force the
agent to use it, and you're 99% sure every metric is calculated the way it
should be.
